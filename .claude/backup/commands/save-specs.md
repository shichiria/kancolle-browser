# /save-specs — セッション会話からの仕様書保存

現在のセッションの会話内容を振り返り、仕様として残すべき内容を抽出して `docs/SPEC/changes/YYYYMMDD_<topic>.md` に保存する。

## 手順

### 1. セッション会話の振り返り

現在の会話を遡り、以下に該当する内容を抽出する:
- ユーザーが述べた要件・仕様・制約
- 設計上の決定事項（なぜその方式を選んだか）
- データ構造・ロジック・API・UIに関する合意事項
- 実装で判明したエッジケースや注意点
- ドメイン知識に基づく仕様の確認結果

以下は**抽出しない**:
- デバッグの過程や試行錯誤
- ツール操作の手順
- 一時的なワークアラウンド

### 2. 仕様書の生成

抽出した内容を機能単位でグルーピングし、以下の構造で作成:

```markdown
# {機能名}

- **日付**: YYYY-MM-DD
- **種別**: 新機能 / 修正 / 拡張 / 仕様確認
- **関連ファイル**: 
  - `path/to/file1.rs` — 概要
  - `path/to/file2.tsx` — 概要

## 概要
何が決まったか、1-3文で。

## 背景・動機
なぜこの仕様になったか。ユーザーの要求や制約。

## 仕様詳細

### データ構造
構造体・型・フィールドの定義。

### ロジック
条件分岐・計算式・状態遷移の説明。

### API/イベント
Tauriコマンド、フロントエンドイベント、APIエンドポイント処理。

### UI
画面・操作に関する仕様。

## 既存SPECとの関連
`docs/SPEC/` 内のどのファイルに関連するか。更新が必要な場合は明記。

## 注意事項
エッジケース、既知の制約、今後の課題。
```

### 3. ファイル保存

- ディレクトリ: `docs/SPEC/changes/`（なければ作成）
- ファイル名: `YYYYMMDD_<topic>.md`（例: `20260404_action-log.md`）
- `$ARGUMENTS` が指定された場合はトピック名として使用
- 1セッションで複数の仕様を議論した場合は機能ごとに別ファイル

### 4. 報告

保存したファイル名と、各ファイルの概要を報告する。
`/update-specs` で既存SPECに統合できる旨を案内する。

## Rules
- 会話の中でユーザーが明言・合意した内容のみ仕様とする（推測で書かない）
- 「こうしましょうか？」の提案は、ユーザーが承認した場合のみ仕様として記録
- 既存SPECファイルは変更しない（`/update-specs` で統合する）
